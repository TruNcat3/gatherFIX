# 五库性能对照实验结果汇总（2026-09-11，共享机器，中位数）

统一问题："修复了 bug，性能有没有变差？" 每库 `tests/bench_perf.py` 可复现。
原则：修复前目标路径若直接崩，则与"修复前可行的 workaround/原生路径"对照；
非目标路径作回归护栏。

## liftfreshFIX (#5743)

| 路径 | 原生 | 修复后 | 比值 |
|---|---|---|---|
| 空张量 torch.tensor([]) | 9.9 µs | 21.5 µs | 2.2x（早退 vs 原生 dispatch，绝对值 ~10µs） |
| 空张量 aten.lift_fresh | 6.7 µs | 17.7 µs | 2.6x（同上） |
| 非空 (67MB) vs clone | 27.1 µs | 66.7 µs | 2.5x（kernel 未动，为框架 host 链既有成本） |

判读：修复核心路径（空张量）修复前=进程崩，修复后可用且只比原生多 ~11µs
（Python dispatch 链）；非空路径 kernel 零改动，与 clone 的差距是框架既有
host 成本（见 pointwiseFIX stage-2 分解：prepare_args+wrapper ≈ 90µs）。

## onehotFIX (#5802) —— 修复同时是性能赢利

| 形状 | 修复前实际路径（composite） | 修复后 Triton | 变化 |
|---|---|---|---|
| (1k,)×1000 类 | 178 µs | 127 µs | **快 40%** |
| (4k,)×16384 类 | 549 µs | 386 µs | **快 42%** |
| (256k,)×32 类 | 5437 µs | 188 µs | **快 27.9x** |
| (128,128)×512 类 | 566 µs | 117 µs | **快 4.8x** |

修复新增的 min/max 值域校验成本：365.7 µs/次（两次 D2H）——大张量下被 kernel
收益淹没；小张量下成为主要开销（已在 README 边界声明，可优化为 kernel 内校验）。

## geluFIX (#5867)

| 路径 | 原生 | gems 修复后 | 比值 |
|---|---|---|---|
| tanh 1MB / 4MB | ~12 µs | ~110 µs | ~9x |
| none 1MB / 4MB | ~11 µs | ~110 µs | ~9x |

判读：tanh 与 none 比值相同（9x）——证明差距是框架 pointwise host 链的既有
成本（原生 ~11µs 是 host 早退下的排队下限，参照 stage-2 分解），**修复本身
零性能影响**（指数 2→2.0 编译期归一）。
泛用层补丁对照：pow(x,2) int 经提升 31.2µs vs pow(x,2.0) 31.1µs——**0% 差异，
数值逐位一致**（max|diff|=0.0）。

## gatherFIX (#5746)

| 路径 | 原生 | gems | 判读 |
|---|---|---|---|
| 连续 index 16x64x256 (1MB) | 5.29 ms | 5.34 ms | **1.0x 持平**（零改动区，与旧报告"噪声内"结论一致且更明确） |
| 连续 index 64x256x512 (17MB) | 160.4 ms | 160.5 ms | **1.0x 持平** |
| 非连续 (64,1,H) expand：修复 strided | — | 0.29 ms | **比 workaround 快 2.4-2.5x** |
| 非连续 workaround（先物化） | 1.03 ms | 0.98-1.07 ms | 修复前的唯一可行路径 |

注：早期 bench 中"原生 0.5ms vs gems 162ms"为异步早退假象（host 返回不等
设备完成），bench_events.py 用 NPU event 计设备时间后澄清：两者设备时间一致。

## 总结论

五个修复**无一引入性能回归**；onehotFIX 和 gatherFIX（非连续路径）还是
显著性能赢利（最快 27.9x / 2.5x）。可见的 gems vs 原生差距（pointwise 类
~9x host 开销）是框架既有成本，已由 pointwiseFIX stage-2 定位（63% 在框架
Python 层）并有 plan-cache 原型（-34%）——修复与性能路线是两条正交的线。
